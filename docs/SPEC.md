# 要件定義書・実装計画書 v1
## 診断×占い 掛け合わせアプリ「ラキカラ」（JK向け）

> **このファイルの使い方**: プロジェクト直下に `docs/SPEC.md` として置き、CLAUDE.md から「実装判断はこの仕様書に従う」と参照させる。実装は §9 のステップ順に、1ステップずつ指示する。

## 1. プロジェクト概要

- **アプリ名**: ラキカラ（決定済み）。ストア表記は `ラキカラ - パーソナルカラー診断＆毎日占い`
  - ブランド名を4文字に抑えてホーム画面のアイコン名が省略されないようにし、検索キーワードはサフィックス側に寄せる
  - bundle ID / package 名: `com.ichirou600.rakikara`（**App Store Connect にアプリレコードを作成した後は変更不可**。Step 0 のレコード作成前に確定させること）
- **ターゲット**: 日本の女子高生（13〜18歳）中心。iPhone比率が非常に高いため iOS 優先、Android 同時対応
- **収益モデル**: 広告（AdMob）＋アフィリエイト（楽天先行、Qoo10後追加）
- **コンセプト**: パーソナルカラー・骨格・星座を「タイプ」としてプロフィール保存し、タイプの掛け合わせで毎日変わる提案（コーデ・ネイル・ヘアアクセ）を返す
- **差別化**: 診断が1回で終わらず、デイリー占いとの掛け合わせで毎日開く理由を作る

## 2. 収益設計

| 収益源 | 配置 | 備考 |
|---|---|---|
| バナー広告 | 全画面下部に常設 | AdMob |
| ネイティブ広告 | 診断結果・おすすめ画面内 | AdMob |
| リワード広告 | 動画視聴で解放コンテンツ（P1） | 単価最高。16分類詳細 or 明日の運勢先読み |
| 楽天アフィリエイト | 「今日のおすすめ」のアイテム検索リンク | 色名＋カテゴリの検索URLにアフィリID付与 |
| Qoo10（後追加） | 同上 | 提携ASP要確認のため v1.1 |

**広告ポリシー上の前提**: 主対象が未成年のため、**非パーソナライズ広告（NPA）を既定**とし、ATT（トラッキング許可）プロンプトは表示しない。AdMobの未成年配慮設定（TFUA等）を有効化。eCPMは下がるが審査・法務リスクを最小化する。

## 3. ゴール / 非ゴール

**ゴール（リリース後30日、仮置き目標）**
- DL→パーソナルカラー診断完了率 70%
- 診断完了者のシェア画像生成率 30%
- DAU/MAU 20%（デイリー占いによる再訪）

**非ゴール（v1では作らない）**
- アカウント登録・ログイン機能（個人情報をサーバーに持たない設計を優先）
- 写真によるAI判定（精度・未成年の顔写真リスク・工数）
- 16分類パーソナルカラー（4分類で開始。16分類はリワード解放のv1.1候補）
- プッシュ通知（v1.1）
- キュレーション型アイテムDB（v1は検索リンク方式で代替）

## 4. 機能要件

### P0（これがないとリリースしない）
1. **パーソナルカラー診断**: 質問10問 → 4分類（イエベ春/ブルベ夏/イエベ秋/ブルベ冬）
2. **骨格診断**: 質問10問 → 3分類（ストレート/ウェーブ/ナチュラル）
3. **プロフィール保存**: PCタイプ・骨格タイプ・誕生日（→星座算出）を端末ローカルのみに保存
4. **今日の占い**: 12星座別。運勢文＋ラッキーカラー（色マスタから選出）＋ラッキーアイテム。サーバーから日次配信
5. **今日のおすすめ（掛け合わせ）**: PCタイプ×ラッキーカラー → コーデ・ネイル・ヘアアクセの提案文＋楽天検索リンク
6. **相性診断**: 自分の星座 × 相手の誕生日入力 → 星座×星座78パターンの静的テキスト
7. **シェア画像生成**: 診断結果カードを画像化して保存・共有シート起動
8. **広告**: バナー＋ネイティブ（リワードはP1）

### P1（リリース後すぐ）
- リワード広告＋解放コンテンツ、Qoo10リンク、プッシュ通知

### P2（設計だけ考慮しておく）
- 16分類PC、推し活要素、写真判定

## 5. データ設計

**アプリ同梱の静的JSON（チャット側で作成 → assets/ に配置）**

| ファイル | 内容 |
|---|---|
| `color_master.json` | 40色。color_id, 色名, hex, 対応PCタイプ[] |
| `type_attributes.json` | PC4種＋骨格3種。似合う色ID[], 素材, キーワード, 説明文 |
| `pc_x_kokkaku.json` | PC×骨格 12通りの「似合うスタイル」テキスト |
| `compatibility.json` | 星座×星座 78通りの相性テキスト |
| `questions.json` | 診断質問と配点（PC10問＋骨格10問） |

**サーバー配信（Firestore、読み取り専用）**
- `daily_fortune/{date}/{zodiac}`: 運勢文, lucky_color_id, lucky_item_category

**端末ローカル（shared_preferences）**
- user_profile: pc_type, kokkaku_type, birthday（サーバーに送信しない）

## 6. 掛け合わせエンジン仕様

- 入力を `(user_profile, daily_fortune, マスタ群)`、出力を `提案カードのリスト` に固定したルール関数のインターフェースを定義する
- **新しい掛け合わせ＝ルール関数を1つ追加するだけ**で画面に反映される構造にする（コンテンツの書き足し不要）
- v1のルール:
  - `todayRecommend()`: PCの似合う色 ∩ 今日のラッキーカラー → 一致ならその色のネイル/ヘアアクセ/コーデ提案＋検索リンク。不一致なら「苦手色は小物・ネイルで少量取り入れる」フォールバック提案
  - `compatibility()`: 星座×星座テキスト
- 検索リンク生成: `色名 + カテゴリ名` で楽天検索URLを組み立て、アフィリエイトIDを付与する共通関数を用意

## 7. システム構成

- **アプリ**: Flutter（iOS / Android 両対応）
- **サーバー**: Firebase
  - Firestore: daily_fortune の配信のみ（ユーザーデータは置かない）
  - Cloud Functions（scheduled、毎朝5:00 JST）: Claude API を呼び、12星座分の占いをJSONで生成 → Firestore へ書き込み
- **AI生成の制約**: プロンプトで「lucky_color は color_master の40色の color_id から選ぶ」「出力は指定JSONスキーマのみ」と固定する（自由生成させるとマッチングが壊れるため）
- **モデル**: 軽量モデル（claude-haiku系）で十分。1日12呼び出しなのでコストはほぼゼロ。最新のモデル名・料金は https://docs.claude.com で確認
- **APIキー**: Cloud Functions の環境変数に置く。**アプリ内には絶対に埋め込まない**

## 8. コンプライアンス・審査要件

- 対象年齢は13歳以上想定。ストアの「子供向け／ファミリー」カテゴリには**登録しない**
- プライバシーポリシーページ必須（個人情報を収集しない旨、誕生日は端末内のみで利用する旨を明記）
- **表現ルール（全コンテンツ共通）**: 骨格・体型は「似合うものの提案」のみ。体型のネガティブ言及・ダイエット誘導・容姿の優劣表現は全面禁止（審査落ち・炎上対策）
- 占いは娯楽目的である旨をアプリ内に注記

## 9. 実装ステップ（Claude Code への指示単位）

| Step | 内容 | 完了条件 |
|---|---|---|
| 0 | リポジトリ作成、Flutter雛形、Codemagic接続、TestFlightへ雛形を1回通す | 実機のTestFlightで雛形アプリが起動する |
| 1 | 静的JSON読込基盤＋プロフィール保存 | マスタを読み込み、プロフィールが再起動後も保持される |
| 2 | PC診断フロー（質問→判定→結果画面） | 10問回答で4分類が正しく判定・保存される |
| 3 | 骨格診断＋PC×骨格の結果表示 | 12通りのテキストが正しく出る |
| 4 | シェア画像生成 | 結果カードが画像保存・共有シートで送れる |
| 5 | 掛け合わせエンジン＋今日のおすすめ（ローカル仮データで） | ラッキーカラー一致/不一致の両パターンが表示される |
| 6 | Firebase接続＋Functionsバッチ（Claude API） | 毎朝、当日の占いがアプリに反映される |
| 7 | 相性診断 | 誕生日入力→78パターンが正しく出る |
| 8 | 広告組込（テストID→本番ID） | バナー・ネイティブが表示される |
| 9 | アフィリリンク・プライバシーポリシー・ストア素材・審査提出 | App Store / Google Play 審査提出完了 |

**Step 0 を最初にやる理由**: 署名・ビルド・申請まわりが初心者最大の詰まりポイントで、最後に発覚すると全工程が止まる。先にパイプラインを貫通させる。「ヒミツ診断」で使っているiOSビルドの仕組みがあれば、そのまま流用する。
